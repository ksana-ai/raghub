# ADR 0004: Preregistered hard benchmark and exact candidate diagnosis

- Status: Accepted
- Date: 2026-08-20

## Context

The preregistered v3 smoke set was useful for proving the Hybrid RRF path, but
both exact Dense and Hybrid reached 1.0 on all four ranking metrics. That
ceiling result does not show whether fusion improves difficult ranking cases
and gives no evidence that another model dependency, such as a reranker, would
repair a real failure.

A reranker can only help when a relevant chunk was generated by at least one
retrieval branch but was ordered outside the final Top K. It cannot recover a
chunk absent from both authorized candidate sets. The evaluation must preserve
that distinction before adding a reranking stage.

## Decision

1. Add `datasets/benchmark/v1.json` as a preregistered 50-query benchmark over
   44 one-chunk documents. Its exact-byte SHA-256 is
   `aa44175b9ae656d97473a8340ebac59bc1432d7cee90e51432c2b4f89e61f85f`.
2. Freeze seven categories before the first retrieval run: exact
   disambiguation, semantic paraphrase, cross-language retrieval,
   near-duplicate distractors, multi-relevant recall, ACL enforcement, and
   tenant isolation. Eight queries have two gold chunks so Recall@K is not
   equivalent to HitRate@K.
3. Bump evaluation reports to `raghub.eval.report/v3`. Each report records the
   authorization-filtered candidate chunk IDs and ranks used by the active
   retrieval mode. Hybrid records the exact FTS and Dense candidate sets used
   by that same request before RRF, not a later reconstruction.
4. Keep candidate evidence internal to evaluation. `model.SearchResult` marks
   it `json:"-"`, so the public search API continues to return only final hits
   and stage traces. The evaluator still checks every branch candidate against
   forbidden chunk IDs; a forbidden candidate fails the safety gate even if it
   was not fused into the final Top K.
5. Evaluate final FTS, Dense, and Hybrid rankings at Top 5 on one clean code
   revision and identical corpus inventory. Also replay standalone FTS and
   Dense at Top 20 to report branch-depth metrics. Candidate-gap
   classification uses the exact candidate sets captured by Hybrid; the
   standalone replays are supporting metrics and do not replace that evidence.
6. Produce `raghub.eval.candidate-diagnosis/v1` with four exhaustive classes:
   `complete`, `fusion_ordering_gap`, `mixed_gap`, and
   `candidate_generation_gap`. Recompute candidate recall and counts from gold
   IDs and recorded candidates instead of trusting caller-provided summaries.
7. Preregister the next-dependency gate. A reranker experiment is warranted
   only when all deterministic gates pass, at least three of the 50 queries
   have incomplete Hybrid recall, and at least half of all missing gold chunks
   are present in the recorded FTS/Dense candidate union. Otherwise the next
   work remains candidate generation, corpus/query coverage, or benchmark
   expansion rather than reranking.
8. Do not edit benchmark v1 query text, documents, or gold/forbidden references
   after observing retrieval output. Any correction or extension requires a
   new dataset version and a new exact-byte hash.

## Consequences

- The benchmark can distinguish “retrieved but misordered” from “never
  retrieved,” which makes the reranker decision falsifiable.
- Capturing branch candidates improves security evidence: authorization leaks
  cannot hide outside the final Top K.
- Candidate IDs increase manifest size but do not change the public API shape.
- Fifty synthetic queries remain local benchmark evidence, not production
  quality or statistical significance. Long documents, document-version
  transitions, and real redacted bad cases still require later datasets.
- Standalone Top-20 Dense replays invoke the embedding provider again. Their
  metrics share profile/config provenance but are not claimed to be the exact
  vectors used by Hybrid; exact classification comes from Hybrid's own captured
  candidates.
